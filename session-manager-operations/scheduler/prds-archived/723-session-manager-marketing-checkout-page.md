# Goal

bilko.run currently has NO marketing/landing page for Session Manager — `/projects/session-manager/` only serves the vendored Web Remote mobile-cockpit SPA (a static-path app per this repo's host-contract, source at `~/Projects/session-manager/web-remote/app`), and its `App.tsx` gates EVERYTHING behind a Clerk `<SignIn/>` wall with zero marketing content. Worse: today the portfolio hub's Session Manager card (`ProjectsPage.tsx`'s `HubRow`, via `card.href`) links straight to that sign-in wall as the PRIMARY action — a dead end for a first-time visitor, since there's no purchase flow there at all and it actively prevents sales. A landing-page + purchase-flow design already exists in the "Session Manager" Claude Design project (`variants/landing-page.jsx` — hero, feature carousel, and a `PurchaseFlow` component) but was never implemented as a real page. Separately, the Stripe backend already has everything needed: `shared/product-catalog.ts` has a `session_manager` catalog entry (commit `9d26b26`) and `/checkout/success` already resolves it correctly and issues a license key. What's missing is the actual page and its wiring to the real `POST /api/stripe/create-checkout-session` endpoint. Build that page, reusing the site's EXISTING checkout/auth pattern (a plain email field via `src/hooks/useAuth.tsx` + `/api/stripe/create-checkout-session` — this site does not use Clerk for product checkout anywhere; don't introduce it) rather than the design mock's placeholder Clerk/Google-sign-in step, and register it as a proper `react-route` project per `docs/host-contract.md` so it shows on the portfolio hub. Once this page is the primary destination, the existing Web Remote app must still be reachable (it's the real product for paired/existing users) — just demoted to a secondary, non-competing action instead of the first thing a prospective buyer hits.

# Implementation notes

Read `docs/host-contract.md` and the `PROJECTS` doc-comment header in `src/data/projectsRegistry.ts` first — they define the three hosting kinds (`react-route`, `static-path`, `external-url`) and this page is explicitly a `react-route` case ('the project is a React page in this monorepo, sharing auth/DB/Stripe'). Do NOT touch `public/projects/session-manager/` — that's the separately-built, separately-owned web-remote mobile cockpit SPA (vendored from the `session-manager` repo's own build), unrelated to this marketing/checkout page; they will coexist at different paths (`/products/session-manager` for this page, `/projects/session-manager/` for the existing app).

Backend contract (already live, do not modify unless the success-page branch in AC needs it): `POST /api/stripe/create-checkout-session` body `{ email, priceType, successUrl?, cancelUrl? }` → `server/routes/stripe.ts`. Catalog entry: `shared/product-catalog.ts` → `{ priceType: 'session_manager', envVar: 'STRIPE_PRICE_SESSION_MANAGER', productKey: PRODUCT_KEYS.SESSION_MANAGER, mode: 'payment' }`. `/checkout/success` handler already branches on `productKey === PRODUCT_KEYS.SESSION_MANAGER` for title/intro copy (see commit `9d26b26ea026556f85130e653d30725342c5ca91`) — read that diff (`git show 9d26b26`) before deciding whether the AC's optional success-page tweak is even needed; it may already be sufficient.

Auth/email pattern: `src/hooks/useAuth.tsx` is a plain email-capture context (`AuthProvider`, `useAuth()`), NOT Clerk — this codebase's Clerk usage (per this same author's other project) is scoped to the session-manager web-remote mobile app's own auth, a completely different system. Reuse `useAuth.tsx` exactly as other product pages (e.g. `PricingPage.tsx`) do — read that file for the concrete pattern of collecting an email and firing the checkout POST.

The Claude Design source project (id `0ca33cd3-c2fa-4644-b728-bde42292abbd`, file `variants/landing-page.jsx`) explicitly marks its login/checkout steps as placeholders ('Clerk auth — wire real keys', 'Buy Me a Coffee SKU — id TBD') — this PRD replaces BOTH placeholders with the real, already-existing site mechanism (email + `/api/stripe/create-checkout-session`), not with newly-invented Clerk/BMC integrations. Reuse the visual tone (serif headline, warm paper/ink palette, carousel) but the interaction logic must match the rest of the site's checkout pages, not the mock.
